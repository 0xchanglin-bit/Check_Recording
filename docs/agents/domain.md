# 領域文件（Domain Docs）

工程技能在探勘程式碼庫時，該怎麼取用這個 repo 的領域文件。

## 開始探勘之前，先讀這些

- repo 根目錄的 **`CONTEXT.md`**，或
- repo 根目錄的 **`CONTEXT-MAP.md`**（如果有的話）——它會指向每個情境各自的 `CONTEXT.md`。跟主題相關的都要讀。
- **`docs/adr/`** — 讀那些跟你即將動工的區域有關的 ADR。在多情境的 repo 裡，也要看 `src/<context>/docs/adr/` 底下該情境專屬的決策。

如果上面這些檔案不在，**就直接往下做，不用出聲**。不要特地標記它們不見了，也不要一開始就建議去建。`/domain-modeling` 技能（會從 `/grill-with-docs` 進來）會等到術語或決策真的被拍板時，才順手把它們建起來。

## 檔案結構

單一情境或多情境的目錄長相，見 `domain-modeling` 的 [`CONTEXT-FORMAT.md`](../domain-modeling/CONTEXT-FORMAT.md)——那是這份結構的單一事實來源。

## 用詞彙表裡的字

當你的產出提到某個領域概念時（在 issue 標題、重構提案、假設、測試名稱裡），就用 `CONTEXT.md` 裡定義好的那個字。不要飄到詞彙表明確要避開的同義詞去。

如果你要用的概念還不在詞彙表裡，這本身就是個訊號——要嘛你在發明專案根本沒在用的說法（那就再想想），要嘛這裡真的有個缺口（把它記下來交給 `/domain-modeling`）。

## 遇到跟 ADR 打架，講出來

如果你的產出跟某個既有的 ADR 相衝突，就直接講明，不要默默把它蓋過去：

> _跟 ADR-0007（event-sourced orders）相衝突——不過值得重新拿出來談，因為……_
